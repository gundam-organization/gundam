Do not add GPU total to host evaluation. Individual medians do not form an

gaps; no occupancy or bandwidth counters were collected.

The response stage takes 2.734 ms even for constant parameters, and 11.507 ms
for global changes. The current `evaluateResponses` kernel visits every dial,
transforms its scalar input and compares it with its previous input before
skipping interpolation. The constant-case timing therefore exposes a substantial
cost that response caching alone has not removed. Attributing that cost specifically
to memory bandwidth would require further profiling.

Five of the six FSI eigen coordinates have response-stage medians near 4.09 ms,
compared with the usual 2.73 ms. Individual coordinates have only two samples;
the highest isolated wall-time outliers should not be treated as stable rankings.
For example, some detector-coordinate outliers have unchanged GPU weight costs
and increased host likelihood or preparation time.

## Optimization order

1. **Sparse response updates.** Build a device index from original scalar
   parameter indices to their dials, detect changed original parameter values,
   and dispatch only the affected responses in cached mode. Eigen-coordinate
   changes can affect several original parameters, so the selection must use
   actual propagation inputs rather than the name of the changed fit coordinate.
   A constant evaluation should skip the response kernel after priming. Preserve
   mirror/clamp semantics, full initialization, and full recomputation after an
   error or rebuild. Keep the existing dense recompute path as a reference.
2. **Event reweight traversal.** The 1.91 ms stage is nearly independent of the
   scenario. Inspect the response-index access pattern and data layout after
   sparse response updates are measured. Do not assume a bandwidth bottleneck
   from elapsed times alone.
3. **Host preparation and likelihood.** Together these measured stages cost
   about 0.87 ms locally. They become more relevant after the GPU scan improves.
4. **Histogram reduction and transfers.** About 0.20 ms combined here; they are
   lower priorities for this workload.

Removing the entire 2.73 ms response stage would give an optimistic ceiling of
about 1.9 times additional speedup for local evaluations. This is not a predicted
gain: sparse selection, dispatch and evaluation of changed dials still have costs.
After each change, replay the same benchmark and the device/error-retry and
fit/covariance regressions before interpreting performance results.

## Follow-up implementation

The first optimization is implemented and its production CUDA passes were
returned from the CC (see below). Model packing
builds a CSR index from original parameter indices to nonconstant dials. Cached
propagation compares the current scalar parameters with the last successful
inputs and sends one compact range per affected parameter to the device. GPU
blocks tile those ranges without scanning unrelated dials. Constant evaluations
skip the response kernel. First propagation, rebuilds and retries after errors
use a full pass; updates affecting more than half of the dials retain the dense
traversal. Per-dial transformed-input comparisons remain active for mirror and
other input semantics. Recompute mode keeps the full traversal.

The extra persistent device index uses four bytes per nonconstant dial. Host
selection time and candidate counts are included in the benchmark output. The
178 host fast tests and the CPU/original fit-covariance test pass locally; the
new GPU test covers multiple ranges, block tails, dense/sparse transitions,
constant/unused parameters, mirroring and rebuilds, but its execution log has
not been included in the production-profile snapshot below.

## Sparse production results

The `cuda-oa2024-profile-sparse` snapshot contains completed runs for both CUDA
modes, with the same V100, Slurm job, four-thread affinity and proposal settings
as the original profile. Its checkout commit is
`b76f2c5d70e71fc75f548233158fbf96e8abb226`. This used the original isolated
process-per-case driver, not the newer resident replacement driver.

The overall run is **incomplete in the received snapshot**: root `summary.json`
says `complete: false`, the CPU log ends during dataset loading at 23%, and
there is no root comparison or final report. There is no error at the end of
that log; the snapshot alone cannot distinguish a still-running job from an
interruption. No new CPU timing is available.

Both CUDA case summaries say `complete: true`. Their resolved model configs
match the previous run. Independent comparison against the **previous CPU
reference** checked matching parameter manifests, model configuration (apart
from backend selection), and all proposal digests. All 2,606 measured likelihoods
per mode and all eight final trial histograms/errors pass the original
`1e-9` relative / `1e-7` absolute tolerances. Maximum absolute differences are
`1.25e-12` for likelihood and `1.25e-11` for histogram contents/errors. This is
a comparison to the historical reference, not a completed same-run CPU check.

|---|---:|---:|---:|---:|
| Constant | 5.792 | 3.075 | 1.884 | 0 |
| One coordinate | 5.788 | 3.090 | 1.873 | 571 |

| All coordinates | 14.568 | 14.581 | 0.999 | 20,340,421 |

For one-coordinate changes the response stage drops from 2.729 to 0.0174 ms,
while host selection costs about 0.0050 ms. The full-evaluation reduction is
about 46.6%. Global updates retain the dense traversal, as intended. Recompute
stays near 14.13 ms for local changes, effectively unchanged.

Event reweighting is now the largest local stage: 1.908 ms, roughly 62% of
the 3.090 ms evaluation. Histogram reduction remains 0.176 ms, and host input
preparation about 0.455 ms. The next profiling target is the event-weight
response-index access pattern and layout; these elapsed times do not by
themselves prove a memory-bandwidth bottleneck. The resident backend replacement
still needs its own CC validation; this isolated run does not exercise it.

An opt-in [event-weight index layout experiment](../../tests/benchmarks/README.md#event-weight-index-layout-experiment)
now implements the next target. It transposes event-dial indices within groups
of 32 events, preserves ordered multiplication, and caps index-buffer padding
at 2x. The benchmark has additional `-interleaved` cases for A/B measurements
in each response mode. No production speedup is claimed for this variant yet.
