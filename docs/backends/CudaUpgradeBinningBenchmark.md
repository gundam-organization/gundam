# CUDA observable migration and smoothing profile

Results returned from the CC on 2026-10-25, generated by
[`229CudaBackendProfiling.py`](../../tests/benchmarks/229CudaBackendProfiling.py).
Raw results are in `cuda-tests-ccl/cuda-upgrade-binning-profile` (untracked).
The reproduction command is in the
[benchmark instructions](../../tests/benchmarks/README.md#cuda-migration-and-smoothing-on-upgrade-cc-2026).

## Workload and provenance

- Tesla V100-SXM2-32GB, Slurm job `62385404`, four host threads.
- `ndUpCcInc.yaml`, with the six overrides recorded in those instructions.
- 277,534 events, 1,778,970 unique dials and 277,534 observable responses.
- `pmuScale` multiplies Pmu; proposals are `1 + N(0, 0.01)`, bounded by its
  domain. Pmu binning is smoothed with fixed width 1 MeV.
- The later `pmuScaleBinningTest.yaml` override disables the Eb parameter set,
  despite the earlier `enableEb2d.yaml`. There are no surface dials in this model.
- Each scenario has three trials of 30 measured evaluations, with five warmup
  evaluations; seed `12345`. Other parameters stay at their initial values.
- Isolated execution: a fresh process loads the model once per backend case.
  Loading takes 74.08 s for each CUDA case and 84.75 s for CPU, outside timings.
- Both CUDA modes use `warpInterleaved` event-dial indices.
- Source checkout commit `b2399e9fc05c7cd77776b53c780699ce73b421eb`.
- All cases load the same build-tree Python module,
  `/sps/t2k/ablanche/build/gundam/src/PythonInterface/GUNDAM.cpython-313-x86_64-linux-gnu.so`,
  SHA-256 `9017b577059d53ee3f29f3759fc4c15992da62216933dedcaffbe4e5127ed2aa`.
  The checkout commit alone does not certify the module's source revision.

## Numerical agreement

Both CUDA cases pass the CPU comparison with relative tolerance `1e-9` and
absolute tolerance `1e-7`. Parameter manifests and seeded proposal digests match.
Every measured likelihood is compared, together with each trial's final normal
and outside histogram contents and errors.

The largest absolute differences across both scenarios and CUDA modes are:

| Quantity | Maximum absolute difference from CPU |
|---|---:|
| Likelihood | 1.07e-13 |
| Normal histogram content/error | 1.36e-12 |
| Outside histogram content/error | 2.66e-15 |

This validates the sampled propagation workload. It does not run a fit, Hesse,
or covariance comparison, nor isolate smoothing against a hard-binning control.

## Evaluation time

Median milliseconds over 90 measured evaluations per scenario and backend.
Speedups use this run's four-thread CPU reference.

| Scenario | CPU | CUDA cached | CUDA recompute | Cached speedup over CPU |
|---|---:|---:|---:|---:|
| Constant parameters | 10.5554 | 1.3123 | 2.3931 | 8.04 |
| Varying pmuScale | 29.9337 | 4.1001 | 5.0905 | 7.30 |

Cached responses are 1.24 times faster than recomputation when pmuScale varies.
The three trial medians for that scenario are 4.101, 4.103 and 4.092 ms for cached
CUDA, versus 29.925, 29.946 and 29.933 ms for CPU.
These are resident evaluation times after loading, not full-fit speedups.

## Dominant stages and state reuse

For varying pmuScale with cached CUDA:

| Stage | Median ms |
|---|---:|
| Complete evaluation (host wall time) | 4.1001 |
| GPU propagation total | 2.8335 |
| Dial response update | 0.0113 |
| Event weights | 0.1055 |
| Observable composition and fused hard-bin search | 1.0066 |
| Fractional contributions and bin-index reconstruction | 1.6353 |
| Histogram reduction | 0.0584 |
| Histogram readback | 0.0320 |
| Host likelihood | 0.0357 |

GPU intervals overlap the complete host evaluation; these columns must not be
added to host wall time. Individual stage medians are not additive either.
The median per-call ratio of observable/search plus contribution/index time to
GPU propagation time is 93.3%. The index interval includes fractional evaluation,
prefix scans, allocation synchronization and stable sorting; this profile does
not identify which of those operations dominates. On CPU, the binning stage
alone takes 17.55 ms, with different stage boundaries from CUDA.

All 277,534 events undergo binning on every measured pmuScale change; the
constant scenario performs no rebinning. This counter measures events processed,
not actual hard-bin crossings. Cached CUDA considers only one dial response per
change, whereas recompute considers all 1,778,970 dials.

The median active contribution count is 279,968.5 during variations, including
outside remainders. CUDA contribution-buffer capacity peaks at 19.23 MiB;
this measures committed/staging/sorted record buffers, not total GPU memory.
Packed event-dial indices occupy another 21.83 MiB. No event-state or event-weight
readbacks occur inside measured evaluations; final histogram checks run outside
the timers.

Further migration optimization would therefore target observable/bin searching
and fractional index construction. Comparing hard and smoothed binning with the
same proposals, or splitting the index timing into its constituent operations,
would be needed to attribute the smoothing cost more precisely.

## Stress baseline and indexed-search retest

`cuda-tests-ccl/cuda-upgrade-binning-stress-profile` adds
`override/pmuScaleBinningStressTest.yaml` after `pmuScaleBinningTest.yaml`.
The recorded proposal sigma is 0.5, with domain `[0.01, 3]`; the smoothing width
stays 1 MeV. Both CUDA comparisons pass. Maximum absolute differences are
`2.33e-10` for likelihood, `1.36e-12` for normal histogram contents/errors and
`3.55e-15` for outside contents/errors.

| Scenario | CPU ms | CUDA cached ms | CUDA recompute ms |
|---|---:|---:|---:|
| Constant parameters | 10.5484 | 1.2912 | 2.2336 |
| Varying pmuScale | 29.9157 | 4.0760 | 5.0005 |

Cached CUDA spends 1.0061 ms in observable/search and 1.6364 ms in contribution/
index construction, close to the 1% baseline despite much larger proposals.
All 277,534 events undergo rebinning per variation. Large displacements therefore
do not remove the dominant cost of the exhaustive implementation.

The next implementation adds an ordered conservative bin hierarchy to all three
search passes and aggregates diagnostic counters per warp. It retains the stable
contribution sort and count/allocation synchronization. Local host regressions
pass; GPU compilation, numerical agreement and speedup require a new CC run.
Repeat both baseline and stress commands with fresh output directories such as
`cuda-upgrade-binning-indexed-profile` and
`cuda-upgrade-binning-stress-indexed-profile`. Retain CPU and both CUDA cases for
numerical comparison. Candidate counts now measure bins surviving tree pruning,
so they intentionally differ from the exhaustive baseline.
